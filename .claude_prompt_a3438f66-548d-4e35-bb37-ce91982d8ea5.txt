# Architecture Design: Node Page Views with Neighborhood Graph

## System Architecture

### Problem Statement

Two issues compound into "clicking a node in the sidebar while in Page view does nothing":

1. **Navigation bug**: `NavTree` leaf clicks call `selectNode(leaf.id)`, which sets `{ selectedId, focus: 'node' }` but does **not** set `view` or `layerId`. When the active `layerId` differs from the clicked node's owning layer — a common scenario when multiple layer sections are expanded — `modelNodePageData` returns `null` at its guard (`n.layer_id !== layerId`, `pageData.ts:506`), and `specNodePageData` fails similarly because `schemaForLayer` looks up the wrong layer. Canvas then shows the empty state "select a node to view its page."

2. **Missing feature**: Node pages exist as a data type (`modelNodePageData` / `specNodePageData` produce valid `PageData` records) but lack the **neighborhood graph** — a small cross-layer ego graph showing the selected node and all its direct connections.

### Navigation Fix

The `NavTree` leaf click handler (`NavTree.tsx:137`) must switch from `selectNode(leaf.id)` to the existing full-navigation actions that already handle layer+view+expansion:

- **Model leaves**: call `navigateToElement(leaf.id, slug)` — `slug` is already in scope as the `LayerRow` prop
- **Schema leaves**: call `navigateToSpecNode(leaf.id, slug)` — same

These actions (`uiStore.ts:182-211`) set `view`, `layerId`, `selectedId`, `focus`, and expand the correct nav tree section+layer. They are already used by `PageView.useNavigate()` for row-click navigation from layer pages, so adopting them in NavTree makes all navigation paths consistent.

The `selectNode` action remains valid for its other call site (URL-restore in `router.tsx`), where the router already sets `view`/`layerId` from search params in the same update cycle.

### Neighborhood Graph Data

A new pure function in `data/` builds the ego graph for a selected node. This follows the established `data/` layer rule: no JSX, no store dependencies, returns typed data.

**For model elements** — walk `model.links` (the same traversal `relationshipsForElement` already does), collect the center node + every directly connected node (any layer), and produce `GraphNodeData[]` + `GraphEdgeData[]`:

```
center node  →  { id: node.id, label: node.name, kind: node.type, domainColor: node.layer_id }
each neighbor →  { id: other.id, label: other.name, kind: other.type, domainColor: other.layer_id }
each link    →  { id: link.id, sourceId, targetId, label: link.type }
```

The `domainColor` is the layer **slug** — the existing `data-domain` CSS selectors in `domain-and-nav.css` will color each node's swatch correctly, even when nodes from 5 different layers appear in the same graph.

**For spec node types** — walk `allRelationshipSchemas(specRaw)` (already called by `specNodePageData`), collect every schema where the selected spec node is source or destination, and build graph data from the schema-level endpoints:

```
center node  →  { id: specNodeId, label: title, kind: 'spec node', domainColor: layerSlug }
each related →  { id: otherSpecNodeId, label: otherTitle, kind: 'spec node', domainColor: otherLayerSlug }
each schema  →  { id: rel.id, sourceId, targetId, label: rel.predicate }
```

The layer slug for each endpoint is derived from the spec node ID prefix (e.g., `"data-model.Entity"` → `"data-model"`).

### Neighborhood Graph Rendering

The `PageView` component renders the neighborhood graph as a fixed-height `GraphCanvas` between the breadcrumb and the description paragraph. This is a read-only context graph, not the full exploration canvas:

- **Layout**: `layout="force"` — small node count (1 center + typically 5–15 neighbors), auto-positions cleanly
- **Height**: Fixed container (~300px), not flex-fill — the page remains a scrollable document
- **Key**: `key={selectedId}` so it remounts (and re-layouts) when navigating between nodes, matching the existing `Canvas.tsx` pattern
- **Selected node**: `selectedNodeId={currentNodeId}` highlights the center node
- **`centerOnSelect`**: Centers the view on the selected (center) node
- **Navigation**: `onNodeSelect` navigates to the clicked neighbor's page (via `navigateToElement`/`navigateToSpecNode`), making the graph an interactive navigation surface
- **No toolbar/controls**: No `GraphToolbar`, no `GraphControls` flyout — this is a small embedded context graph, not the full graph exploration mode
- **Structural edges**: Pass `isStructuralEdge` for consistent edge classification

The `PageData` type gains an optional `neighborhood` field carrying the graph data. When absent or empty, the graph area is not rendered (e.g., a node with zero connections).

### View Integration

The `PageView` component currently receives a `PageData` record and is a pure renderer. The neighborhood graph data should be part of this record rather than fetched independently, keeping the single-source-of-truth pattern. The `usePageData()` hook already has access to `model`, `index`, and `specRaw` — the neighborhood builder reads from the same inputs.

`Canvas.tsx`'s page-mode branch (`isPage ? ... : ...` at line 457) renders `<PageView pg={pg} />` — no changes needed there. The graph embeds inside `PageView`'s scroll area, not as a sibling.

## Scalability Design

### Data Volume

The neighborhood computation for model elements walks `model.links` once — the same `O(L)` traversal that `relationshipsForElement` already performs. For the reference model (~445 links), this is negligible. The result set is bounded by the node's actual degree (typically 5–20 neighbors), so rendering cost is constant regardless of total model size.

For spec nodes, `allRelationshipSchemas` iterates all 12 layer schemas — also trivial and already called by `specNodePageData`.

Both traversals are already happening inside the page data builders. The neighborhood builder can share the intermediate results (outgoing/incoming lists) rather than walking the links a second time.

### Memoization

The `usePageData()` hook's `useMemo` dependency array (`[view, layerId, selectedId, focus, model, index, specRaw]`) already covers every input the neighborhood builder needs. No additional memoization layer is required — the neighborhood data is computed as part of the same `useMemo` call that builds the rest of `PageData`.

### Rendering

`GraphCanvas` with `layout="force"` handles small graphs efficiently. The fixed-height container prevents layout thrashing in the scroll area. Keying by `selectedId` ensures a clean remount on navigation rather than incremental updates to a running force simulation.

## Established Patterns

### Pattern: `data/` layer purity

All graph data builders (`modelGraph.ts`, `specGraph.ts`, `relationships.ts`, `pageData.ts`) are pure functions that take API payloads and return typed data. The neighborhood builder follows this exactly — takes `model`/`index`/`specRaw`, returns `GraphNodeData[]` + `GraphEdgeData[]`. No JSX, no store access.

### Pattern: `domainColor` = layer slug

Every existing graph node uses `domainColor: layerId` (the layer slug string), not a hex color. The CSS rules in `domain-and-nav.css` (`.graph-node[data-domain="<slug>"] .graph-node__swatch`) apply the actual color. The neighborhood graph follows this — a node from `data-model` gets `domainColor: "data-model"` regardless of which layer's page is showing. This is the mechanism that makes cross-layer nodes visually identifiable.

### Pattern: Navigation actions set full context

`navigateToElement` and `navigateToSpecNode` (`uiStore.ts:182-211`) are the "full-context navigation" actions — they set `view`, `layerId`, `selectedId`, `focus`, and expand the nav tree. `selectNode` is the "minimal" action (only `selectedId` + `focus`). The fix uses the full-context actions everywhere navigation crosses layer boundaries, which is exactly what they were built for.

### Pattern: `GraphCanvas` keyed by state

`Canvas.tsx:474` keys the full graph by `${view}:${layerId}:${graphLayout}:${nodeMarginPreset}` to force remount and re-center on context change. The neighborhood graph follows this pattern with `key={selectedId}`.

### Pattern: `PageData` as a single record

All page content flows through one `PageData` object returned by `usePageData()`. Adding neighborhood graph data as an optional field on `PageData` keeps this pattern — `PageView` receives everything it needs in one prop.

### Pattern: `PageNavTarget` for navigation

Table rows and breadcrumbs carry `PageNavTarget` objects that `PageView.useNavigate()` translates to store actions. The neighborhood graph's `onNodeSelect` would use the same dispatch mechanism — determine whether the clicked node is a model element or spec node, then call the corresponding navigation action. Since `onNodeSelect` gives a node ID (not a `PageNavTarget`), the translation happens in the component, consistent with how `Canvas.tsx:478` handles graph node clicks.

**Files**: `NavTree.tsx`, `uiStore.ts`

- When `sectionId === 'spec'`: call `navigateToSpecNode(leaf.id, slug)`

No changes needed to `selectNode` itself — it remains valid for URL-restore.

### 2. Build the neighborhood graph data function

**Files**: `data/pageData.ts` (or a new `data/neighborhoodGraph.ts` — either fits the `data/` layer)

Add a pure function that takes the same inputs the page data builders already receive and returns `{ nodes: GraphNodeData[], edges: GraphEdgeData[] } | null`:

**Model element neighborhood**: Given `model`, `index`, and `elementId`:
1. Look up the center node via `index.byUuid.get(elementId)`
2. Walk `model.links`, resolve endpoints, collect links where center is source or target
3. Build a `Map<string, GraphNodeData>` of the center + all neighbors (dedup by UUID)
4. Set each node's `domainColor` to its `layer_id`
5. Build `GraphEdgeData[]` from the collected links
6. Return `null` if no connections exist

**Spec node neighborhood**: Given `specRaw` and `specNodeId`:
1. Call `allRelationshipSchemas(specRaw)` (share with `specNodePageData` if built inline)
2. Filter schemas where `source_spec_node_id` or `destination_spec_node_id` === `specNodeId`
3. Build `Map<string, GraphNodeData>` of the center + all related node types
4. Derive layer slug from each spec node ID prefix for `domainColor`
5. Resolve display labels via `specNodeTitle()` (already exists in `pageData.ts:309`)
6. Build `GraphEdgeData[]` from the relationship schemas
7. Return `null` if no relationships exist

### 3. Extend `PageData` with neighborhood graph data

**Files**: `data/pageData.ts`

Add an optional field to the `PageData` interface:

```ts
neighborhood?: {
  nodes: GraphNodeData[];
  edges: GraphEdgeData[];
  centerId: string;
};
```

`centerId` tells the renderer which node to highlight/select. `GraphNodeData` and `GraphEdgeData` are imported from `@tinkermonkey/heimdall-ui`.

Populate this field in both `modelNodePageData` and `specNodePageData` by calling the neighborhood builder. The builder can share the link traversal already being done for the outgoing/incoming tables, avoiding a redundant walk.

`layerPageData` does not set this field — layer pages show the layer-level overview, not a node ego graph.
